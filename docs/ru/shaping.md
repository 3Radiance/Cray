# Слои формирования трафика: `jitter` и `fragment`

Оба слоя это обычные обёртки. Они принимают любой поток и возвращают поток: без сокетов, без файлов профилей и без знания о транспорте или протоколе ниже и выше. Работают на клиенте и на сервере, в `inbound.layers` или в `outbound.layers`, в любом месте между слоем-источником (`tcp` или `unix`) и протоколом.

Они затрагивают только **запись**. Чтение проходит без изменений, поэтому каждая сторона формирует тот трафик, который сама отправляет, и настраивать оба конца одинаково не нужно.

```toml
[[outbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[outbound.layers]]
type = "jitter"
stages = [
    { bytes = 2000, delay = "0" },
    { delay = "1-10" },
]

[[outbound.layers]]
type = "fragment"
stages = [
    { bytes = 2000, size = "1-1" },
    { size = "600-1000" },
]

[[outbound.layers]]
type = "vless"
uuid = "11111111-1111-4111-8111-111111111111"
```

Оба слоя работают **стадиями** (`stages`): каждая стадия действует на свой
префикс соединения, последняя стадия без `bytes` покрывает весь остальной трафик.
`bytes` это суммарное число уже записанных байт, при достижении которого слой
переходит к следующей стадии.

## `jitter`

Перед каждой записью ждёт случайное время и только потом передаёт данные дальше.

```toml
[[outbound.layers]]
type = "jitter"
stages = [
    { bytes = 2000, delay = "0" },
    { delay = "10-20" },
]
```

Каждая стадия это `{ bytes, delay }`:

- `bytes` (опционально) — верхняя граница стадии в байтах, суммарно записанных
  через слой. Когда счётчик достигает `bytes`, слой переходит к следующей стадии.
  У последней стадии `bytes` не указывается: она действует до конца соединения.
- `delay` — строка с миллисекундами:

| Значение | Смысл |
|---|---|
| `"15"` | фиксированная задержка 15 мс |
| `"10-20"` | случайная задержка на каждую запись: от 10 мс до 20 мс включительно |
| `"0"` | без задержки |

`min` не должен быть больше `max`. Если `stages` не указан, задержка равна `"0"` на всё соединение.

Как это работает:

- Задержка применяется **на каждый вызов записи**, а не на каждый байт. Одна большая запись задерживается один раз, туннель, который пересылает много маленьких кусков, задерживается на каждый кусок.
- Во время задержки вызывающий код ждёт (обратное давление). Ничего не буферизуется.
- Чтение никогда не задерживается.
- Пропускная способность ограничена величиной `размер записи / задержка`. При записях по 16 КиБ и средней задержке 25 мс одно направление не превысит примерно 640 КиБ/с. Держите задержки небольшими или примите цену на объёмном трафике.
- Случайные числа берутся из генератора с инициализацией на соединение (`fastrand::Rng` на каждый стрим). Распределение равномерное, генератор не криптографический.

Что слой делает и чего не делает: jitter меняет **момент**, когда пакеты уходят. Размеры и направления он не меняет, а равномерная случайная задержка не имитирует никакое реальное приложение. Считайте его способом сломать простую корреляцию по времени, а не маскировкой.

## `fragment`

Режет каждую запись на более мелкие части.

```toml
[[outbound.layers]]
type = "fragment"
stages = [
    { bytes = 2000, size = "1-1" },
    { size = "1000-1400" },
]
```

Каждая стадия это `{ bytes, size }`:

- `bytes` (опционально) — та же верхняя граница в суммарно записанных байтах,
  что и у `jitter`. Последняя стадия без `bytes` действует до конца соединения.
- `size` — строка:

| Значение | Смысл |
|---|---|
| `"1400"` | части не больше 1400 байт |
| `"500-1000"` | размер каждой части случайный в `[500, 1000)`, выбирается на каждую часть; `min` должен быть больше 0 |
| `"50%"` | каждая часть равна заданному проценту от записи (от 1 до 100) |

Если `stages` не указан, размер равен `"1400"` на всё соединение.

Как это работает:

- Каждый вызов записи нарезается на части выбранного размера внутри одного вызова:
  слой последовательно пишет куски во внутренний поток, пока буфер не кончится.
  Вызывающий код видит одну завершённую запись, а вниз по цепочке уходит серия
  более мелких записей подряд.
- Стадии позволяют резать только начало соединения (например, первые байты
  с ClientHello), а остальной трафик резать крупнее или не резать вовсе.
- Записи, которые уже меньше выбранного размера, проходят без изменений.
- Слой не добавляет пауз. Станут ли соседние части отдельными TCP-сегментами, решает ядро: при `TCP_NODELAY` каждая запись обычно уходит сразу, но записи, сделанные, пока очередь отправки занята, могут склеиться. Чтобы развести их по времени, поставьте в цепочку слой `jitter`.

### Куда ставить

Позиция определяет, что именно режется:

| Цепочка | Эффект |
|---|---|
| `tcp → fragment → tls → ...` | фрагментатор видит вывод TLS, включая **ClientHello**, и разбивает его на несколько TCP-записей |
| `tcp → tls → fragment → ...` | открытые записи режутся до TLS, поэтому TLS создаёт более мелкие записи |
| `tcp → fragment → protocol` | режет собственные байты протокола, для цепочек без TLS |

Это только техника разбиения. Слой не умеет отправлять поддельные пакеты, менять TTL, переставлять сегменты или трогать опции TCP, поэтому он не заменяет инструменты, работающие на уровне сырых пакетов.

### Важно: мелкие нарезки и `jitter`

Если режешь TLS ClientHello (или просто начальные байты) мелко, например
по `1-1`, то **на этом участке байт джиттер должен быть выключен** (`delay = "0"`).
Когда `jitter` стоит ниже `fragment` в цепочке (`tcp → jitter → fragment → ...`),
каждый нарезанный кусок проходит через отдельную задержку: 2000 байт по 1 байту
это ~2000 записей, и даже задержка 1–10 мс (в среднем ~5 мс) даст ~10 секунд
только на ClientHello — handshake не дождётся, сокет отвалится по таймауту.

Правило: мелкая нарезка — нулевой джиттер, джиттер включается только дальше,
на крупных кусках. Эталон из `test.toml`:

```toml
[[outbound.layers]]
type = "jitter"
stages = [
    { bytes = 2000, delay = "0" },
    { delay = "1-10" },
]

[[outbound.layers]]
type = "fragment"
stages = [
    { bytes = 2000, size = "1-1" },
    { size = "600-1000" },
]
```

Здесь первые 2000 байт (ClientHello) режутся по 1 байту без задержек,
а дальше идут куски 600–1000 байт с джиттером 1–10 мс.

## Логирование

Оба слоя пишут каждую запись на уровне `trace` с тегами `JITTER` и `FRAG`:

```bash
RUST_LOG=info,JITTER=trace,FRAG=trace ./cray --config client.toml
```

## Подводные камни

- Неверный `delay` или `size` внутри `stages` обнаруживается при загрузке конфига, прокси не стартует с такой конфигурацией. Проверяйте конфиг до деплоя.
- `fragment` с размером больше вашего MTU заметного эффекта не даёт, потому что ядро всё равно режет большие записи.
- Верхняя граница диапазона у `fragment` не включается (`"1000-1400"` никогда не даст ровно 1400), а у `jitter` включается (`"10-20"` может дать и 20). `"10-10"` в обоих случаях всегда даёт 10.
- `stages` должен содержать хотя бы одну стадию: пустой список уронит соединение на первой записи.
- Оба слоя на каждом соединении стоят пропускной способности и добавляют задержку. Измеряйте, прежде чем включать их для объёмного трафика.
