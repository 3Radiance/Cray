# Слой `xhttp2` (Split HTTP/2)

Слой `xhttp2` реализует разделение туннеля на два независимых HTTP/2-потока в рамках одного соединения (Split HTTP):
1. **Upload (клиент ──▶ сервер):** запрос с методом из конфигурации (обычно `POST`). Клиент пишет исходящие байты в тело запроса, а сервер их читает (`RecvStream`).
2. **Download (сервер ──▶ клиент):** запрос с методом `GET`. Сервер отправляет ответ и пишет байты в тело ответа (`SendStream`), а клиент читает их из ответа (`ResponseFuture`).

Оба потока связываются между собой на сервере с помощью уникального случайного 32-символьного hex Session ID (`sid`), передаваемого в кастомном HTTP-заголовке.

Слой работает в одном из двух режимов, который задаёт обязательный параметр `mode`:

- **`StreamUp`** — upload это один долгоживущий `POST`, тело которого стримится. Минимальные накладные расходы, но нужен путь, на котором не буферизуется тело запроса (см. [«За CDN и reverse proxy»](#за-cdn-и-reverse-proxy)).
- **`PacketUp`** — каждый кусок upload отправляется отдельным коротким `POST` с порядковым номером, а сервер собирает пакеты обратно по порядку. Медленнее, но работает через посредников, которые буферизуют тела запросов (например, CDN).

## Кастомный заголовок Session ID (`id`)

Слой `xhttp2` **не навязывает фиксированное имя заголовка** для Session ID. Имя заголовка полностью определяется через профиль HTTP/2 (`config`), где в таблице `[http_headers]` для нужного заголовка указывается специальное значение `"id"`:

```toml
# conf/http2.toml
[http_headers]
"x-session-id" = "id"          # Сюда Cray подставит сгенерированный Session ID
"user-agent"   = "Mozilla/5.0 (Windows NT 10.0; Win64; x64)"
"accept"       = "*/*"
```

### Как это работает:
- **Значение `"id"`** — это маркер для Cray.
- **На клиенте (`outbound`):** перед отправкой запросов `POST` и `GET` слой генерирует случайный 32-значный hex идентификатор (`sid`) и подставляет его значением в указанный заголовок.
- **На сервере (`inbound`):** сервер находит в профиле заголовок, у которого значение `"id"`, и извлекает Session ID из входящих запросов клиента для корреляции пары `POST` и `GET`.
- **Имя заголовка может быть любым допустимым HTTP-заголовком**, например:
  - `"x-session-id" = "id"`
  - `"x-correlation-id" = "id"`
  - `"sec-ch-ua-session" = "id"`
- **⚠️ Требование:** и клиенту, и серверу в своём файле профиля **обязательно** нужно иметь заголовок со значением `"id"` как для upload-ноги (метод слоя), так и для download-ноги (`GET`). Заголовок ищется в секции соответствующей ноги (`[uplink]`/`[downlink]`), а при её отсутствии — в общем наборе `headers_order`/`[http_headers]`. Если в какой-то ноге заголовок со значением `"id"` не найден, конфигурация слоя не соберётся с ошибкой `XHTTP2 needs a header with the value id (.../uplink|downlink)`.

## Заголовок порядкового номера (`seq`, только PacketUp)

В режиме `PacketUp` в профиле для upload-ноги нужен ещё один заголовок со специальным значением `"seq"`. Клиент подставляет в него порядковый номер пакета (десятичное `u64`, начиная с `0`, плюс один на каждый `POST`), а сервер по нему восстанавливает порядок:

```toml
[uplink.http_headers]
"x-session-id" = "id"
"x-seq"        = "seq"
```

- Имя заголовка любое, как и для `id`.
- Номер есть только у upload-ноги; у `GET` его нет.
- Сервер: если у upload-ноги нет заголовка `"seq"`, соединение завершается ошибкой `XH2 requires an seq header` (проверяется при приёме соединения, а не при старте). Клиент: ничего не проверяется, но без заголовка сервер отклонит каждый `POST`, поэтому профили на обеих сторонах нужно держать согласованными.
- Запрос без `seq` или с нечисловым значением отклоняется как любой другой некорректный запрос (см. [«Отказы»](#отказы)).

## Конфигурация слоя

Слой `xhttp2` настраивается одинаково просто как на клиенте, так и на сервере:

```toml
# Клиент (outbound)
[[outbound.layers]]
type = "xhttp2"
host = "example.com"
path = "/split-tun"
method = "POST"
config = "conf/http2.toml"
mode = "StreamUp"   # или "PacketUp"

# Сервер (inbound)
[[inbound.layers]]
type = "xhttp2"
host = "example.com"
path = "/split-tun"
method = "POST"
config = "conf/http2.toml"
mode = "StreamUp"   # или "PacketUp"
```

### Параметры

| Поле | Тип | Описание |
|---|---|---|
| `host` | строка | Обязательно. Хост / `:authority` запроса. На сервере запросы с другим хостом отклоняются с кодом `reject_status` (по умолчанию 404). |
| `path` | строка | Обязательно. Путь (`:path`), на который отправляются и ожидаются запросы. Все остальные пути получают `reject_status`. |
| `method` | строка | Обязательно. Метод для upload-ноги (`POST`, `PUT` и т.д.). Download-нога всегда использует `GET`. |
| `config` | строка | Обязательно. Путь к файлу профиля HTTP/2 (нужен и outbound, и inbound, чтобы знать заголовок с `id`). |
| `mode` | строка | Обязательно. `StreamUp` или `PacketUp` (регистр важен). На клиенте и сервере должен совпадать. Пропущенное или неизвестное значение ломает сборку слоя (`need mode` / `unknown mode <значение>`). |

## Профиль: uplink и downlink, ответы и отказы

Заголовки запросов можно задавать отдельно для upload-ноги (`[uplink]` — любой метод, кроме `GET`) и отдельно для download-ноги (`[downlink]` — всегда `GET`). Старый плоский формат продолжает работать: верхнеуровневые `headers_order` и `[http_headers]` служат общим фолбэком для обеих ног. Внутри каждой ноги — те же `headers_order` и `http_headers`, при частичном задании недостающее берётся из верхнего уровня (у `[uplink]` есть алиасы `[post]`/`[put]`, у `[downlink]` — `[get]`):

```toml
[uplink]
headers_order = ["x-session-id", "user-agent", "content-type"]

[uplink.http_headers]
"x-session-id" = "id"
"user-agent" = "Mozilla/5.0"
"content-type" = "application/grpc"

[downlink]
headers_order = ["x-session-id", "user-agent"]

[downlink.http_headers]
"x-session-id" = "id"
"user-agent" = "Mozilla/5.0"
```

### Ответы сервера

- `[uplink.response]` / `[downlink.response]` — заголовки успешных (200) ответов на соответствующий запрос. Формат тот же: `headers_order` + `http_headers`.
- Если `response` у ноги не задан, используется верхнеуровневая таблица `[response]` (общий фолбэк); если нет и её, ответ содержит только `content-type: application/octet-stream`.
- В заголовках ответа (как и в запросных) значение `"id"` подменяется на Session ID.
- Если в ответных заголовках не указан `content-type`, слой ставит `application/octet-stream`.

### Отказы

Запросы, не совпавшие по пути, хосту, методу или с отсутствующим/битым Session ID, отклоняются:

- `reject_status` — код отказа, любое значение 100–999 (по умолчанию `404`); некорректный код ломает загрузку профиля.
- `[reject]` — заголовки отказа в том же формате; при отсутствии таблицы отказ остаётся голым (только статус).
- `body_path` внутри `[reject]` — путь к файлу (обычно HTML), целиком отдающемуся телом отказа. Файл читается один раз при загрузке профиля, отсутствие файла — ошибка конфигурации. Если `content-type` в `[reject.http_headers]` не задан, при наличии тела подставляется `text/html`.

```toml
reject_status = 505

[response]
headers_order = ["server"]

[response.http_headers]
server = "nginx"

[uplink.response]
headers_order = ["content-type", "data"]

[uplink.response.http_headers]
content-type = "application/grpc"
data = "id"               # подменяется на Session ID

[reject]
headers_order = ["server", "content-type"]
body_path = "conf/reject.html"

[reject.http_headers]
server = "nginx"
content-type = "text/html; charset=utf-8"
```

`reject_status`, `[reject]` и `[response]` работают и в слое `http2` (без uplink/downlink — одним общим набором, см. [http2.md](http2.md)).

## Архитектура: StreamUp

```
Клиент (Outbound)                                        Сервер (Inbound)
─────────────────                                        ────────────────
[ChunkStream]                                            [ChunkStream]
    │                                                        │
    ├─▶ TX: POST /split-tun (тело запроса) ───▶ RX (чтение) ─┤
    │       Header: x-session-id: <sid>                      │
    │                                                        │
    └─◀ RX: GET  /split-tun (тело ответа)  ◀─── TX (запись) ─┘
            Header: x-session-id: <sid>
```

- Порядок прихода запросов на сервер не имеет значения: если первым пришел `POST`, его поток чтения сохраняется до прихода `GET`. Если первым пришел `GET`, его дескриптор ответа ждет прихода `POST`.
- Данные стримятся чанками (`ChunkStream`) без полной буферизации в памяти.
- Окно управления потоком HTTP/2 автоматически обновляется при чтении данных.

## Архитектура: PacketUp

```
Клиент (Outbound)                                           Сервер (Inbound)
─────────────────                                           ────────────────
[ChunkStream]                                               [ChunkStream]
    │                                                           │
    ├─▶ TX: POST seq=0 ┐                                        │
    │       POST seq=1 ├─ параллельно, любой порядок ──▶ Reorder (на sid) ─▶ RX
    │       POST seq=2 ┘                                        │
    │                                                           │
    └─◀ RX: GET (одно длинное тело ответа) ◀─────────── TX (запись) ─┘
```

- Клиент отправляет `GET` один раз. Сервер сразу отвечает `200` (заголовки из `[downlink.response]`) и стримит весь download в теле этого ответа; на `POST` он не ждёт.
- Каждая запись режется на куски не больше 16 КиБ. Каждый кусок это отдельный `POST` со своим `seq` и закрытым телом запроса (`END_STREAM`). Параллелизм ограничен HTTP/2 `max_concurrent_streams`: перед следующим `POST` клиент ждёт свободный слот стрима.
- Сервер хранит по одной сессии на `sid` в общей для процесса таблице, поэтому `POST`-ы и `GET` одной сессии могут прийти по разным HTTP/2-соединениям (так и бывает за reverse proxy, который открывает соединение на каждый запрос).
- Пакеты проходят через буфер реордера своей сессии: пакет с ожидаемым `seq` отдаётся сразу вместе со всеми подряд идущими уже накопленными пакетами; пакет «из будущего» ждёт в буфере, пока не заполнится пропуск.
- На `POST` сервер отвечает пустым `200` только после того, как пакет принят буфером реордера.
- Конец потока: клиент отправляет `POST` с пустым телом и следующим `seq` (FIN). Когда все предыдущие данные отданы, сервер закрывает сессию, а читающая сторона получает EOF.
- Ошибки: отсутствующий `seq` или тело больше 16 КиБ отклоняются с `reject_status`. Дубликат или уже отданный `seq` тоже отклоняется, и дополнительно сессия закрывается.

## За CDN и reverse proxy

Каждую ногу посредник может сломать по-своему. Заметки из запуска `xhttp2` за Cloudflare → nginx → Cray:

- **Буферизация тела запроса (`StreamUp`).** CDN может держать тело `POST` до его конца, и сервер вообще не видит поток. `content-type = "application/grpc"` на upload-`POST` (при включённом gRPC на CDN) заставляет Cloudflare стримить его. Ставь его **только** в `[uplink.http_headers]`: на `GET` он делает запрос похожим на битый gRPC, и `GET` не доходит до origin. Если CDN буферизует всё равно, используй `PacketUp`.
- **Кеширование `GET`.** CDN кеширует по расширению файла (Cloudflare по умолчанию кеширует `.css` и подобные), а ключ кеша это просто URL, поэтому твой `x-session-id` не играет роли: отдаётся закешированная копия, и `GET` туннеля до сервера не доходит. Симптом: `POST`-ы приходят, а `GET` нет. Как предотвратить:
  - отвечай на `GET` заголовком `cache-control: no-store` (`[downlink.response.http_headers]`);
  - никогда не отдавай с того же URL кешируемую заглушку (`max-age`, `immutable`): любой посетитель без сессии положит её в кеш CDN;
  - добавь правило CDN, обходящее кеш для пути туннеля (Cloudflare: Cache Rule с *Bypass cache* или Cache Response Rule, добавляющее `no-store`), и потом сделай purge URL;
  - либо используй путь без кешируемого расширения.

  Проверка: `curl -s -o /dev/null -D - --http2 -H "x-session-id: $(openssl rand -hex 16)" https://host/path | grep -iE 'cf-cache-status|age'` — статус не должен быть `HIT`.
- **Буферизация download.** Рекомендуемые заголовки ответа downlink: `content-type: text/event-stream` и `x-accel-buffering: no` (см. `conf/xhttp2.toml`). В nginx также поставь `proxy_buffering off;` и `proxy_request_buffering off;`.
- **Маскировка перед слоем.** Прокси может отдавать страницу-заглушку запросам без сессии; следи, чтобы заглушка не кешировалась (см. выше) и чтобы имя заголовка сессии, по которому решает прокси, совпадало с профилем для **обеих** ног.
