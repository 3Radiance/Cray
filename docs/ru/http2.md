# Настройка HTTP/2-отпечатка

HTTP/2-отпечаток (в стиле Akamai: хеш по SETTINGS, размерам окон, приоритетам и порядку заголовков) полностью настраивается через файл HTTP/2-профиля, на который слой `http2` указывает через `config`. Клиентский слой `http2` формирует всё, что видно в сети: connection preface, фрейм SETTINGS, приоритеты потоков, порядок псевдозаголовков и порядок заголовков (`src/fingerprint/http2/`).

В отличие от форвардящего прокси, Cray **сам создаёт** HTTP/2-запрос. Входящих заголовков браузера, которые можно было бы пропустить дальше, нет: запрос строится из параметров слоя (`method`, `host`, `path`) и конфигурации заголовков в профиле.

## Как работает слой

Клиент (`outbound.layers`):

```
tls stream ──▶ http2 layer ──▶ virtual stream ──▶ protocol
                 1. HTTP/2 handshake с профилированным builder'ом (таймаут 5 секунд)
                 2. один запрос: method + :authority + :path из слоя,
                    заголовки из профиля, END_STREAM на HEADERS НЕ ставится
                 3. тело запроса — направление upload,
                    тело ответа — направление download
```

Сервер (`inbound.layers`):

```
tls stream ──▶ http2 layer ──▶ один virtual stream на каждый принятый запрос ──▶ protocol
                 1. HTTP/2 server handshake (таймаут 5 секунд)
                 2. на каждый запрос, у которого совпали method, path и host, отвечаем 200,
                    на всё остальное — 404
                 3. каждый принятый запрос становится независимым потоком байтов
```

Слой берёт соединение и отдаёт наружу **виртуальный поток**. Для протокола сверху это обычный поток байтов, как TCP-сокет: записанные байты уходят как DATA-фреймы в теле запроса (клиент) или в теле ответа (сервер), а читаемые байты приходят из противоположного направления. Управление потоком (`WINDOW_UPDATE`) обрабатывается внутри слоя. Закрытие стороны записи отправляет пустой DATA-фрейм с `END_STREAM`.

Профиль формирует только клиентскую сторону. Сервер его игнорирует и использует фиксированные настройки (128 одновременных потоков, окно потока 1 МиБ, окно соединения 4 МиБ).

## Параметры слоя

```toml
[[outbound.layers]]
type = "http2"
path = "/tun"
host = "example.com"
method = "POST"
config = "./http2.toml"
```

| Поле | Клиент | Сервер |
|---|---|---|
| `path` | обязательно: `:path` запроса | обязательно: запросы должны совпадать, остальные получают 404 |
| `method` | обязательно: `POST` или `PUT` | обязательно: запросы должны совпадать, остальные получают 404 |
| `host` | обязательно: `:authority` запроса | обязательно: запросы должны совпадать, остальные получают 404 |
| `config` | обязательно: путь к HTTP/2-профилю | не используется |
| scheme | всегда `https` | н/д |

Профиль это отдельный файл только с ключами верхнего уровня (заголовка `[http2]` нет). Относительные пути отсчитываются от рабочей директории процесса. Профиль загружается на первом соединении и кэшируется по пути, поэтому ошибки в нём проявятся тогда, а после правок нужен перезапуск. Ключи, которых нет в профиле, молча игнорируются.

## Пример профиля (`http2.toml`)

```toml
# http2.toml
connection_window_update = 15663105
settings_order = [
    "HEADER_TABLE_SIZE",
    "ENABLE_PUSH",
    "INITIAL_WINDOW_SIZE",
    "MAX_FRAME_SIZE",
]
pseudo_headers_order = [":method", ":authority", ":scheme", ":path"]
headers_order = ["user-agent", "accept", "accept-language", "priority"]
# initial_stream_id = 3             не указывайте, чтобы значение вычислилось само

[settings]
header_table_size = 65536
enable_push = false
initial_window_size = 6291456
max_frame_size = 16384

[headers_priority]
exclusive = true
depends_on = 0
weight = 255

[http_headers]
user-agent = "Mozilla/5.0 (...)"
accept = "*/*"
accept-language = "en-US,en;q=0.6"
priority = "u=0, i"
```

В TOML нет `null`. Чтобы оставить необязательное поле незаданным, просто опустите ключ. Скалярные ключи пишите раньше первой таблицы.

### `settings`: значения фрейма SETTINGS

Значения, объявляемые во фрейме SETTINGS. Опущенные необязательные ключи не отправляются. `enable_push` — обычный булев флаг и должен присутствовать всегда, когда есть `[settings]`:

| Поле | Значение |
|---|---|
| `header_table_size` | Размер динамической таблицы HPACK. Опустите, чтобы не отправлять. |
| `enable_push` | Server push вкл/выкл. Отправляется всегда. |
| `max_concurrent_streams` | Максимум одновременно активных потоков. Опустите, чтобы не отправлять. |
| `initial_window_size` | Окно управления потоком для каждого стрима. |
| `max_frame_size` | Максимальный размер полезной нагрузки фрейма. |
| `max_header_list_size` | Максимальный размер списка заголовков. Опустите, чтобы не отправлять. |

Если таблица `[settings]` отсутствует целиком, ничего не кастомизируется и применяются значения библиотеки по умолчанию.

### `settings_order`: порядок параметров SETTINGS

Порядок параметров в исходящем фрейме SETTINGS. Отправляются только параметры, присутствующие в `settings`, и именно в этом порядке:

```
HEADER_TABLE_SIZE
ENABLE_PUSH
MAX_CONCURRENT_STREAMS
INITIAL_WINDOW_SIZE
MAX_FRAME_SIZE
MAX_HEADER_LIST_SIZE
```

Имена нечувствительны к регистру. Неизвестное имя приводит к ошибке соединения при создании builder'а, так что опечатка проявится на первом же `h2`-соединении, а не незаметно даст неверный отпечаток.

### `connection_window_update`: окно соединения

Начальное окно управления потоком на уровне соединения, независимое от `initial_window_size` для отдельных стримов. Если не задано, используется значение библиотеки по умолчанию. Настоящие браузеры используют здесь характерные большие значения (например, `15663105` у Firefox), так что это поле важнее, чем кажется.

### `initial_stream_id`: первый стрим запроса

Явный ID первого потока, инициированного клиентом. Если не задан, вычисляется:

- нет priority-фреймов: `1`;
- есть priority-фреймы: наибольший настроенный `stream_id` приоритета плюс 2 (priority-фреймы занимают ID потоков до первого настоящего запроса).

Если задаёте вручную вместе с `priority_frames`, выбирайте свободный нечётный ID после них. Коллизия ломает соединение.

### `priority_frames`: PRIORITY-фреймы перед запросом

PRIORITY-фреймы, отправляемые перед потоком запроса (классический сигнал дерева приоритетов Firefox), записываются как массив таблиц:

```toml
[[priority_frames]]
stream_id = 3
exclusive = false
depends_on = 0
weight = 201

[[priority_frames]]
stream_id = 5
exclusive = false
depends_on = 0
weight = 101
```

| Поле | Значение |
|---|---|
| `stream_id` | Поток, к которому привязан приоритет (клиентские потоки нечётные). |
| `exclusive` | Является ли зависимость эксклюзивной. |
| `depends_on` | ID родительского потока (`0` = корень соединения). |
| `weight` | Сырое значение, от 0 до 255. |

Опустите ключ или оставьте его пустым, если priority-фреймы не нужны. В примере выше без `initial_stream_id` поток запроса получит ID `7`.

### `headers_priority`: зависимость потока в HEADERS

Приоритет, прикрепляемый к фрейму HEADERS запроса:

```toml
[headers_priority]
exclusive = true
depends_on = 0
weight = 255
```

Те же поля, что у priority-фрейма, кроме `stream_id`. Опустите таблицу, если кастомная зависимость не нужна.

### `pseudo_headers_order`: порядок псевдозаголовков

Порядок `:method`, `:path`, `:authority`, `:scheme` в запросе. Неизвестное имя приводит к ошибке соединения. Браузеры здесь характерно различаются; Firefox отправляет `:method, :authority, :scheme, :path`:

```toml
pseudo_headers_order = [":method", ":authority", ":scheme", ":path"]
```

Задавайте явно. Сами значения берутся из слоя (`method`, `host`, `path`) и фиксированной схемы `https`.

### `headers_order` и `http_headers`: заголовки запроса

Список заголовков запроса строится только из этих двух полей:

1. Идём по `headers_order` по порядку. Для каждого имени берём значение из `http_headers`. Имя, которое указано в порядке, но не имеет значения в `http_headers`, **пропускается**, потому что входящего запроса, откуда его можно было бы скопировать, нет.
2. Добавляем заголовки, которые есть в `http_headers`, но отсутствуют в `headers_order`. Их взаимный порядок **не определён**.

```toml
headers_order = ["user-agent", "accept", "accept-language", "priority"]

[http_headers]
user-agent = "Mozilla/5.0"
accept = "*/*"
accept-language = "en-US,en;q=0.6"
priority = "u=0, i"
```

Из этого следуют правила:

- **Перечисляйте все заголовки в `headers_order`.** Всё, что не указано, добавляется в неопределённом порядке.
- **Используйте ключи в нижнем регистре в `http_headers`.** Имена ищутся в нижнем регистре, поэтому ключ вроде `User-Agent` никогда не совпадёт, и заголовок будет отброшен.
- Значения должны быть корректными значениями HTTP-заголовков; неверное имя или значение приводит к ошибке соединения.
- Слой не добавляет собственных заголовков, даже `content-type` или `content-length`. Всё, что хотите видеть, добавляйте в `http_headers`.

## Стриминг

Тела стримятся в обоих направлениях и никогда не буферизуются целиком. Один туннель — это один HTTP/2-поток, и одно HTTP/2-соединение пока несёт один туннель от клиента (мультиплексирование нескольких туннелей в одном соединении запланировано).

Клиент не ждёт заголовков ответа перед первой записью. Они читаются лениво при первом чтении из потока, поэтому протокол, который сначала отправляет, а потом слушает, не зайдёт в дедлок с сервером, отвечающим только после чтения.

## Связь с ALPS

Когда в TLS-профиле `alps = true`, те же `settings` и `settings_order` перекодируются в TLS ALPS-нагрузку для `h2` (см. [tls.md](tls.md)). Браузеры используют именно такую кодировку, так что один профиль управляет обоими местами в сетевом трафике. Слой TLS находит его через `http2_path`; укажите там тот же файл, что и в `config` слоя `http2`. Держите их синхронизированными с браузером, которому подражаете: расхождение между фреймом SETTINGS и ALPS-нагрузкой само по себе является признаком отпечатка.

## Подводные камни

- `settings_order` и `pseudo_headers_order` валидируются: неизвестные имена ломают соединение, а не деградируют молча. Сверяйте написание со словарями выше.
- `enable_push` должен присутствовать, когда есть таблица `[settings]`.
- Значения `settings` вне допустимого протоколом диапазона (например, абсурдный `max_frame_size`) отклоняются HTTP/2-стеком при handshake.
- `initial_stream_id`, совпадающий с ID из `priority_frames`, убивает соединение. Лучше опустить его и дать вычислиться самому.
- Ключи `http_headers` должны быть в нижнем регистре, и каждый заголовок должен быть указан в `headers_order`, чтобы получить определённую позицию.
- Сервер принимает только запросы, у которых method, path и host совпадают со слоем; всё остальное получает 404. Клиент и сервер с разными `path`, `method` или `host` никогда не соединятся.
- Сервер сравнивает `host` с хостом из `:authority` без порта. Пишите `host = "example.com"`, а не `"example.com:443"`. За обратным прокси значением будет то, что прокси передаёт как `:authority`.
- Клиентскому слою `http2` нужен `config`. Слою TLS нужен `http2_path` только при `alps = true`; указывайте один и тот же файл.
- Неизвестные ключи игнорируются без предупреждения (в том числе прежний `end_stream_on_headers`). Если настройка не действует, сначала проверьте написание ключа.
- Чтобы проверить результат, снимите трафик клиента (Wireshark) или логируйте JA3/JA4 и HTTP/2-отпечаток на стороне сервера (например, в nginx) и сравните со снимком настоящего браузера, которому подражаете.
