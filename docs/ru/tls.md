# Настройка TLS-отпечатка 

Клиентский слой `tls` полностью формирует `ClientHello` на основе файла TLS-профиля, на который указывает слой: порядок наборов шифров, расширения и их порядок, кривые, алгоритмы подписи, ALPN, GREASE и сжатие сертификатов. Каждый байт `ClientHello`, учитываемый при определении отпечатка, находится под вашим контролем. Используется BoringSSL через `btls` / `tokio-btls` (`src/fingerprint/tls/`).

Серверный слой `tls` — обычный акцептор соединений. Он **не подстраивается под определённый отпечаток**: ему нужны только сертификат, ключ и список ALPN.

## Где находятся настройки

TLS-отпечаток хранится в **отдельном файле профиля**, на который слой `tls` указывает через `tls_path`. В профиле только ключи верхнего уровня (заголовка `[tls]` нет). Сам слой содержит параметры соединения:

```toml
# client.toml
[[outbound.layers]]
type = "tls"
sni = "example.com"
tls_path = "./tls.toml"        # профиль, описанный в этом документе
http2_path = "./http2.toml"    # читается только при alps = true
```

```toml
# tls.toml (профиль)
cipher_suites = [ ... ]
# ...
```

```toml
# server.toml
[[inbound.layers]]
type = "tls"
cert = "/path/to/fullchain.pem"
key = "/path/to/privkey.pem"
tls_path = "./tls.toml"        # на сервере из него читается только `alpn`
```

Поля слоя:

| Поле | Клиент | Сервер |
|---|---|---|
| `sni` | обязательно: имя в `ClientHello`, по нему же проверяется сертификат | не используется |
| `tls_path` | обязательно: профиль отпечатка | обязательно: читается только `alpn` |
| `http2_path` | обязательно, но файл читается только при `alps = true`; иначе подойдёт любая строка-заглушка | не используется |
| `cert`, `key` | не используются | обязательны: цепочка сертификатов и закрытый ключ в PEM |

Как обрабатываются файлы:

- Относительные пути отсчитываются от рабочей директории процесса, а не от файла конфигурации.
- Профиль загружается, когда он впервые понадобился соединению, и кэшируется по пути. Ошибки в профиле проявятся на первом соединении, а не при запуске, а после правок нужен перезапуск.
- Ключи, которых нет в профиле, молча игнорируются, поэтому опечатка в имени ключа просто ничего не меняет.
- Отсутствие обязательного поля слоя обнаруживается, когда приходит соединение.

В TOML нет значения `null`. Чтобы оставить необязательное поле незаданным, **просто не указывайте соответствующий ключ**.

## Процесс установления соединения

Клиент (`outbound.layers`):

```text
tcp socket ──▶ tls layer ──▶ next layer (http2, protocol, ...)
                 1. Берётся SslConnector для `tls_path` (создаётся один раз на файл профиля и кэшируется)
                 2. Установка SNI из слоя и добавление данных ALPS, если alps = true
                 3. Рукопожатие с выбранным профилем, тайм-аут 6 секунд
                 4. Проверка сертификата сервера и возврат зашифрованного потока
```

Сервер (`inbound.layers`):

```text
tcp socket ──▶ tls layer ──▶ next layer (http2, protocol, ...)
                 1. SslAcceptor (mozilla_intermediate) с цепочкой сертификатов и ключом
                 2. Callback выбора ALPN с учётом порядка предпочтений клиента
                 3. Рукопожатие, тайм-аут 6 секунд
```

Callback ALPN перебирает список клиента по порядку и выбирает первый протокол, который также присутствует в списке `alpn` сервера. Если совпадений нет, ALPN не согласовывается.

Клиентский коннектор собирается в `tls_builder` (`src/fingerprint/tls/builder.rs`) в следующем порядке: хранилище корневых сертификатов Chromium → наборы шифров → ALPN → кривые → алгоритмы подписи → ограничение размера записи → сжатие сертификатов → GREASE → перестановка расширений → OCSP → SCT → билет сессии → делегированные учётные данные → порядок расширений. ALPS добавляется отдельно для каждого соединения.

### Проверка сертификата сервера

Клиент проверяет сертификат сервера по хранилищу корневых сертификатов Chromium и сверяет имя хоста со значением `sni`. Используйте сертификат, которому доверяет публичный центр сертификации (например, Let's Encrypt) и имя которого совпадает с `sni`. Самоподписанные сертификаты и частные центры сертификации пока не поддерживаются.

## Пример конфигурации

```toml
# tls.toml
cipher_suites = [
    "TLS_AES_128_GCM_SHA256",
    "TLS_AES_256_GCM_SHA384",
    "TLS_CHACHA20_POLY1305_SHA256",
    "ECDHE-ECDSA-AES128-GCM-SHA256",
    "ECDHE-RSA-AES128-GCM-SHA256",
    "ECDHE-ECDSA-AES256-GCM-SHA384",
    "ECDHE-RSA-AES256-GCM-SHA384",
]
alpn = ["h2", "http/1.1"]
curves = ["X25519", "P-256", "P-384"]
signature_algorithms = [
    "ecdsa_secp256r1_sha256",
    "rsa_pss_rsae_sha256",
    "rsa_pkcs1_sha256",
    "ecdsa_secp384r1_sha384",
    "rsa_pss_rsae_sha384",
    "rsa_pkcs1_sha384",
]
cert_compression = ["brotli"]
permute_extensions = false
grease_enabled = false
status_request = false
signed_certificate_timestamp = false
session_ticket = false
alps = false
# extensions_order = [ ... ]    не указывайте, если не нужен фиксированный порядок
# delegated_credentials = [ ... ]
# record_size_limit = 16385
```

На практике параметры `cipher_suites`, `curves` и `signature_algorithms` обязательны: если какой-либо из них не указан, в BoringSSL передаётся пустой список, который библиотека отклоняет, из-за чего соединение завершается ошибкой.

### `cipher_suites`: строгий порядок, два блока

Список объединяется через `:` и передаётся в `set_cipher_list`. При этом используется `set_preserve_tls13_cipher_list(true)`, чтобы заданный порядок сохранялся без изменений.

BoringSSL хранит наборы шифров TLS 1.3 и TLS 1.2 в двух отдельных внутренних списках. Объединить их в произвольном порядке невозможно: BoringSSL всегда выводит их двумя последовательными блоками — сначала TLS 1.3, затем TLS 1.2, независимо от того, как они перемешаны в конфигурации. Настоящие браузеры ведут себя так же, поэтому это ограничение не требует обходных решений.

Для TLS 1.3 используются имена наборов шифров в формате IANA `TLS_<AEAD>_<HASH>`. Для TLS 1.2 используются короткие имена в стиле OpenSSL, например `ECDHE-ECDSA-AES128-GCM-SHA256`.

TLS 1.3:

```text
TLS_AES_128_GCM_SHA256
TLS_AES_256_GCM_SHA384
TLS_CHACHA20_POLY1305_SHA256
```

TLS 1.2:

```text
ECDHE-ECDSA-AES128-GCM-SHA256
ECDHE-ECDSA-AES256-GCM-SHA384
ECDHE-RSA-AES128-GCM-SHA256
ECDHE-RSA-AES256-GCM-SHA384
ECDHE-ECDSA-CHACHA20-POLY1305
ECDHE-RSA-CHACHA20-POLY1305
ECDHE-ECDSA-AES128-SHA
ECDHE-RSA-AES128-SHA
ECDHE-RSA-AES128-SHA256
ECDHE-ECDSA-AES256-SHA
ECDHE-RSA-AES256-SHA
TLS_RSA_WITH_AES_128_GCM_SHA256
TLS_RSA_WITH_AES_256_GCM_SHA384
TLS_RSA_WITH_AES_128_CBC_SHA
TLS_RSA_WITH_AES_256_CBC_SHA
TLS_RSA_WITH_3DES_EDE_CBC_SHA
TLS_PSK_WITH_AES_128_CBC_SHA
TLS_PSK_WITH_AES_256_CBC_SHA
ECDHE-PSK-AES128-CBC-SHA
ECDHE-PSK-AES256-CBC-SHA
ECDHE-PSK-CHACHA20-POLY1305
```

### `alpn`: список протоколов

Список кодируется в сетевом формате с префиксами длины и отправляется серверу на стороне клиента либо используется как список принимаемых протоколов на сервере. Пустые записи и записи длиной более 255 байт молча пропускаются.

Если `alpn` не указан, ALPN не отправляется и не принимается. В таком случае слой `http2` не сможет работать поверх этого TLS-соединения. **На сервере установите `alpn = ["h2"]` в профиле, на который указывает `tls_path`, если цепочка содержит слой `http2`.**

### `curves`: поддерживаемые группы в заданном порядке

Параметр передаётся в `set_curves_list`. Полный список поддерживаемых BoringSSL значений:

```text
P-256
P-384
P-521
X25519
X25519Kyber768Draft00
X25519MLKEM768
MLKEM1024
```

### `signature_algorithms`: алгоритмы подписи в заданном порядке

Параметр передаётся в `set_sigalgs_list`. Полный список поддерживаемых значений:

```text
rsa_pkcs1_md5_sha1
rsa_pkcs1_sha1
rsa_pkcs1_sha256
rsa_pkcs1_sha256_legacy
rsa_pkcs1_sha384
rsa_pkcs1_sha512
ecdsa_secp256r1_sha256
ecdsa_secp384r1_sha384
ecdsa_secp521r1_sha512
rsa_pss_rsae_sha256
rsa_pss_rsae_sha384
rsa_pss_rsae_sha512
ed25519
```

### `extensions_order`: точные позиции расширений

Управляет расположением каждого расширения TLS в исходящем `ClientHello` (внутри используется `set_extension_permutation`).

Здесь следует перечислить каждое расширение, активное во время рукопожатия. Активность расширений зависит от параметров `cipher_suites`, `curves`, `signature_algorithms`, `alpn`, `cert_compression`, `record_size_limit` и других.

**Если активное расширение не указано в списке, его позиция не определена**: оно может быть удалено, добавлено в конец или размещено где угодно. Документация используемой библиотеки не даёт гарантий на этот счёт. Всегда перечисляйте все включённые вами расширения.

Поддерживаемые имена (некоторые имеют псевдонимы):

```text
server_name
status_request
ec_point_formats
signature_algorithms
alpn
padding
signed_certificate_timestamp
extended_master_secret
quic_transport_parameters_legacy
quic_transport_parameters_standard (или quic_transport_parameters)
cert_compression
session_ticket
supported_groups
pre_shared_key
early_data
supported_versions
cookie
psk_key_exchange_modes
certificate_authorities
signature_algorithms_cert
key_share
renegotiation_info
delegated_credentials
application_settings
application_settings_old
encrypted_client_hello (или ech)
next_proto_neg (или npn)
channel_id
record_size_limit
```

Неизвестное имя приведёт к ошибке соединения `unknown extension: <name>`.

`renegotiation_info` (RFC 5746) нельзя включить или отключить отдельно: BoringSSL всегда отправляет это расширение, как и любой современный браузер. В списке нужно указать только его позицию.

### `cert_compression`: настоящие декомпрессоры

Каждое имя регистрирует работающий декомпрессор, поэтому рукопожатие завершается успешно даже в том случае, если сервер отправляет сжатый сертификат:

```text
brotli
zlib
zstd
```

Неизвестные имена вызывают ошибку, а не пропускаются молча.

### Логические переключатели

- **`permute_extensions`** — случайным образом меняет порядок расширений при каждом рукопожатии (поведение Chrome). **Не используйте этот параметр одновременно с заполненным `extensions_order`**: фиксированный и случайный порядок противоречат друг другу, поэтому для каждого профиля нужно выбрать один вариант. Стиль Chrome: `true`, GREASE включён, фиксированный порядок не задан. Стиль Firefox: фиксированный порядок и `false`.
- **`grease_enabled`** — добавляет значения GREASE (случайные неизвестные идентификаторы наборов шифров и расширений). Алгоритмы JA3/JA4 обычно удаляют GREASE перед вычислением хеша, поэтому этот параметр меняет передаваемые по сети байты, но не хеш.
- **`status_request`** — запрос OCSP stapling. Браузеры отправляют его по умолчанию.
- **`signed_certificate_timestamp`** — расширение SCT для Certificate Transparency. В браузерах оно также включено по умолчанию.
- **`session_ticket`** — определяет, отправляется ли расширение `session_ticket`. Коннектор создаётся отдельно для каждого соединения, поэтому возобновление сессии не происходит; параметр управляет только наличием расширения в отпечатке.
- **`alps`** — Application-Layer Protocol Settings (настройки протокола прикладного уровня). Отправляет данные ALPS для `h2`, сформированные на основе тех же `settings` и `settings_order`, которые управляют настоящим кадром HTTP/2 SETTINGS (см. [http2.md](http2.md)). Браузеры используют именно такое кодирование, поэтому отдельная конфигурация ALPS не нужна. HTTP/2-профиль читается из файла, указанного в `http2_path` слоя TLS. Если `settings` или `settings_order` отсутствует, полезная нагрузка будет пустой.

### `delegated_credentials`: расширение, включаемое по желанию

Включает расширение TLS `delegated_credentials`. Значение — список имён алгоритмов подписи, которые могут использоваться делегированными учётными данными. Чтобы не включать расширение, не указывайте этот ключ.

```text
ecdsa_secp256r1_sha256
ecdsa_secp384r1_sha384
ecdsa_secp521r1_sha512
ed25519
ecdsa_sha1
```

### `record_size_limit`: целое число

Объявляет максимальный размер записи TLS, который клиент готов принимать (расширение `record_size_limit`, 16-битное значение). Чтобы не включать расширение, не указывайте этот ключ.

## ECH (пока не реализовано)

Параметры `enable_ech`, `enable_ech_grease` и `doh` принимаются парсером конфигурации, но **в настоящее время игнорируются**: коннектор их не использует, поэтому они не добавляют и не удаляют расширение ECH.

Если нужно указать позицию `encrypted_client_hello` в `ClientHello`, добавьте его в `extensions_order`. Сама полезная нагрузка ECH пока не формируется. Поиск ECH через DoH запланирован.

## Примечания по JA3 / JA4

- JA3 вычисляет хеш упорядоченного списка наборов шифров, списка расширений, кривых и форматов точек. Все четыре компонента контролируются здесь; форматы точек соответствуют настройкам BoringSSL по умолчанию для выбранных кривых.
- JA4 дополнительно учитывает ALPN, наличие SNI (позицию `server_name` в `extensions_order`) и количество элементов.
- Перед вычислением хеша алгоритмы удаляют идентификаторы GREASE, поэтому `grease_enabled` влияет на поведение промежуточных сетевых устройств, но не на сам хеш.

## Важные нюансы

- Параметры `cipher_suites`, `curves` и `signature_algorithms` должны быть заданы. Если список не указан, он становится пустым, и BoringSSL отклоняет его.
- Поле `http2_path` должно быть задано в клиентском слое `tls`, даже если `alps = false`. Файл читается только при `alps = true`, так что в остальных случаях подойдёт заглушка.
- В `extensions_order` должны быть перечислены **все активные расширения**, иначе их позиции не определены. Если сомневаетесь, перехватите настоящий `ClientHello` браузера, например с помощью `tls.peet.ws` или Wireshark, и воспроизведите его порядок.
- Одновременное использование `permute_extensions = true` и `extensions_order` создаёт противоречивую конфигурацию. Выберите один вариант.
- Если на сервере используется слой `http2`, в профиле, на который указывает его слой `tls`, необходимо установить `alpn = ["h2"]`, иначе рукопожатие HTTP/2 завершится ошибкой.
- Акцептор сервера кэшируется только по паре `cert` и `key`. Если два слоя `tls` используют одну пару, но разные файлы `tls_path`, применится первый профиль.
- Неизвестные ключи в профиле игнорируются без предупреждения. Если настройка не действует, сначала проверьте написание ключа.
- Сертификат сервера должен быть доверенным для хранилища корневых сертификатов Chromium, а его имя должно совпадать с `sni`.
- На один файл конфигурации приходится один профиль. Чтобы использовать другой отпечаток, запустите ещё один экземпляр с другим конфигурационным файлом.
