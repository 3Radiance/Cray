# Cray

[English](README.md) | Русский

Кастомный прокси-движок на Rust.

Cray строится на **модульной слоёвой архитектуре**: транспорт и протокол независимы друг от друга. Можно написать свой протокол, не думая о том, как байты доедут по сети, или написать свой транспорт, не думая о протоколе. Из слоёв собирается любой сценарий прямо в конфиге:

```
tcp → кастомный протокол
tcp → tls → кастомный протокол
tcp → tls → http2 → кастомный протокол
```

Готовых слоёв пока немного, но с каждым новым протоколом или транспортом число возможных пайплайнов растёт.

> 🚧 Проект в активной разработке. Основная архитектурная идея уже работает, но дыр ещё много (см. [Статус](#статус)).

---

## Как это работает

Конфигурация это TOML-файл. В начале указывается роль, `client` или `server`, чтобы прокси не путал функции и методы вызовов. Дальше описываются две цепочки слоёв:

- **`inbound.layers`**: как принять соединение;
- **`outbound.layers`**: как выйти дальше.

Роль меняет смысл слоёв: на клиенте inbound это вход браузера, а outbound это туннель до сервера; на сервере inbound это приём туннеля, а outbound это выход в интернет.

**Правила цепочки:**
- первый слой это источник соединений (`tcp` или `unix`);
- остальные слои это транспорты, каждый превращает поток в поток;
- **протокол всегда последний** в цепочке и завершает соединение.

### Слои

| Слой | Клиент | Сервер |
|---|---|---|
| `tcp` | inbound: слушает `addr`. outbound: подключается к `addr` | inbound: слушает `addr`. outbound: без `addr` это прямое соединение к цели (как «freedom/direct») |
| `unix` | inbound: слушает `addr`. outbound: подключается к `addr`| inbound: слушает `addr`. outbound: подключается к `addr` |
| `http_connect` | принимает HTTP CONNECT от браузера и достаёт адрес назначения | не используется |
| `tls` | клиентское рукопожатие: `sni` и настраиваемый отпечаток | акцептор: рукопожатие с вашими сертификатами |
| `http2` | открывает POST/PUT-запрос и отдаёт наружу **виртуальный стрим** | HTTP/2-сервер: принимает стримы и отдаёт каждый дальше как отдельный поток |
| `jitter` | добавляет случайную задержку перед каждой записью; см. [docs/ru/shaping.md](docs/ru/shaping.md) | то же, для трафика, который отправляет сервер |
| `fragment` | режет каждую запись на более мелкие части; см. [docs/ru/shaping.md](docs/ru/shaping.md) | то же, для трафика, который отправляет сервер |
| `tsf` | протокол (тестовый) | протокол (тестовый) |

Слой `http2` или любой мультиплексирующий транспорт забирает сокет, а наружу отдаёт виртуальный стрим. Поэтому протоколу всё равно, что под ним: голый TCP, TLS или HTTP/2. Он просто читает и пишет поток.

### Пример: клиент

```toml
role = "client"

# 1. вход: слушаем локальный порт и разбираем HTTP CONNECT
[[inbound.layers]]
type = "tcp"
addr = "127.0.0.1:10810"

[[inbound.layers]]
type = "http_connect"

# 2. выход: туннель до сервера
[[outbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[outbound.layers]]
type = "tls"
sni = "domain.com"
tls_path = "./tls.toml"
http2_path = "./http2.toml"   # читается только при alps = true

[[outbound.layers]]
type = "http2"
path = "/tun"
host = "idk.com"
method = "POST"
config = "./http2.toml"

[[outbound.layers]]
type = "tsf"      # протокол всегда последний
magic = 432
```

Что происходит:

1. `tcp` в inbound слушает адрес (это делает любой inbound независимо от роли).
2. `http_connect` достаёт из запроса адрес назначения и передаёт его протоколу, чтобы тот пометил пакеты. На этом inbound закончен. Вместо HTTP CONNECT можно написать свой входной слой, например SOCKS5: его задача только достать адрес назначения.
3. В outbound `tcp` создаёт сокет и подключает его к серверу, `tls` шифрует его, `http2` оборачивает в виртуальный стрим, а протокол работает уже с ним.

### Пример: сервер

```toml
role = "server"

[[inbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[inbound.layers]]
type = "tls"
cert = "/path/to/fullchain.pem"
key = "/path/to/privkey.pem"
tls_path = "./tls.toml"      # на сервере из него читается только alpn

[[inbound.layers]]
type = "http2"
path = "/tun"
host = "idk.com"
method = "POST"

[[inbound.layers]]
type = "tsf"
magic = 432

[[outbound.layers]]
type = "tcp"        # без адреса: подключаемся туда, куда попросил протокол
```

Здесь те же слои, но работают они как акцепторы:

- `tls` принимает сокет, делает рукопожатие с вашими сертификатами и отдаёт его дальше;
- `http2` это HTTP/2-сервер: принимает только запросы с совпадающими `method`, `path` и `host`, остальным отвечает 404;
- затем вызывается **серверная функция протокола**, которой передаётся стрим;
- `tcp` в outbound без адреса подключается к цели, которую назвал протокол.

## Настройка отпечатков

И TLS, и HTTP/2 настраиваются целиком. Cray умеет задавать значения вручную, профилей пока что нету.

```toml
# tls.toml
cipher_suites = [
    "TLS_AES_128_GCM_SHA256",
    "TLS_AES_256_GCM_SHA384",
    "TLS_CHACHA20_POLY1305_SHA256",
    "ECDHE-ECDSA-AES128-GCM-SHA256",
    "ECDHE-RSA-AES128-GCM-SHA256",
]
alpn = ["h2"]
curves = ["X25519", "P-256", "P-384"]
signature_algorithms = [
    "rsa_pkcs1_sha256",
    "rsa_pkcs1_sha384",
    "ecdsa_secp256r1_sha256",
]
permute_extensions = true
```

Отпечатки лежат в отдельных файлах профилей, на которые указывают слои: `tls_path` (TLS) и `config` (HTTP/2). HTTP/2-профиль `http2.toml` описывает SETTINGS, порядок псевдозаголовков и заголовков, приоритеты.

Подробное описание всех полей: [docs/ru/tls.md](docs/ru/tls.md) и [docs/ru/http2.md](docs/ru/http2.md).

На сервере для h2 нужно `alpn = ["h2"]` в профиле, на который указывает `tls_path` слоя `tls`.

## Модули

| Модуль | Роль |
|---|---|
| `inbound/` | Входные слои: `tcp`, `unix`, `http_connect`, как свой (например, SOCKS5) |
| `transport/` | Транспортные слои: `tls`, `http2` и обёртки `jitter`, `fragment` |
| `protocol/` | Протокол: последний слой цепочки |
| `outbound/` | Выход: прямое соединение или цепочка слоёв |
| `auth/` | Базовая криптография и методы аутентификации (в разработке) |
| `config/` | Загрузка и проверка конфигурации |
| `fingerprint/` | TLS/HTTP2 билдеры |

## Запуск

Для сборки нужны Rust, `cmake` и C/C++-компилятор (TLS построен на BoringSSL через `btls`).

```bash
cargo build --release
cd conf          # пути к профилям вроде ./tls.toml отсчитываются от рабочей директории
../target/release/cray --config client.toml
../target/release/cray --config server.toml
```

Примеры конфигов и профилей лежат в [`conf/`](conf/).

### Логирование

Уровень по умолчанию `debug`. Чтобы изменить его, задайте `RUST_LOG`, глобально или для отдельных тегов:

```bash
RUST_LOG=info ./cray --config server.toml
RUST_LOG=info,H2=debug,FRAG=trace ./cray --config client.toml
```

Теги: `CFG`, `INB`, `LISTEN`, `CHAIN`, `TLS`, `H2`, `TCP`, `TSF`, `CERT`, `JITTER`, `FRAG`. Подробности по каждому соединению пишутся на уровнях `debug` и `trace`, поэтому `info` остаётся тихим.

## Статус

Работает:
- слои `tcp`, `unix`, `tls`, `http2`, `http_connect` и обёртки `jitter`, `fragment`;
- сборка цепочки из конфига для клиента и сервера, проверка порядка слоёв;
- тестовый протокол `tsf`.

> ⚠️ `tsf` это **тестовый протокол без аутентификации**. Не используйте его в реальной сети.

**Планы:**
1. Нормальный протокол с аутентификацией и защитой от повторов (nonce-кэш).
2. `auth/`: верификаторы и генераторы.
3. Двухуровневая проверка: уровень 1 на стороне nginx (HMAC-кука, timestamp, при отсутствии куки честный статик-сайт), уровень 2 в протоколе (при отказе зеркало настоящей страницы ошибки, а не TCP RST).
4. Декларативное описание протокола (DSL) для тех, кто не хочет писать Rust-код. Rust-авторы остаются со свободными руками, DSL ограничен закрытым набором верификаторов.
5. Свои транспорты и протоколы как расширения, HTTP/1.1 и WebSocket поверх, UDP.
6. Мультиплексирование соединений (в последнюю очередь).
