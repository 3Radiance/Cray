# Cray

[English](README.md) | Русский

[![CI](https://github.com/3Radiance/Cray/actions/workflows/ci.yml/badge.svg)](https://github.com/3Radiance/Cray/actions/workflows/ci.yml)

Кастомный прокси-движок на Rust.

Cray строится на **модульной слоёвой архитектуре**: транспорт и протокол независимы друг от друга. Можно написать свой протокол, не думая о том, как байты доедут по сети, или написать свой транспорт, не думая о протоколе. Из слоёв собирается любой сценарий прямо в конфиге:

```
tcp → кастомный протокол
tcp → tls → кастомный протокол
tcp → tls → http2 → кастомный протокол
```

Готовых слоёв пока немного, но с каждым новым протоколом или транспортом число возможных пайплайнов растёт.

> 🚧 Проект в активной разработке. Основная архитектурная идея уже работает, но дыр ещё много (см. [Статус](#статус)).

---

## Как это работает

Конфигурация это TOML-файл с двумя цепочками слоёв:

- **`inbound.layers`**: как принять соединение;
- **`outbound.layers`**: как выйти дальше.

Флагов `client`/`server` больше нет: поведение следует из позиции. Inbound-слои слушают и принимают, outbound-слои звонят. Терминальный слой (протокол) в конце outbound — эта сторона инициирует; в конце inbound — принимает.

**Правила цепочки:**
- первый слой это источник соединений (`tcp` или `unix`);
- остальные слои это транспорты, каждый превращает поток в поток;
- **протокол всегда последний** в цепочке и завершает соединение.

### Слои

| Слой | outbound | inbound |
|---|---|---|
| `tcp` | подключается к `addr`; без `addr` — прямое соединение к цели (как «freedom/direct») | слушает `addr` |
| `unix` | подключается к `addr` | слушает `addr` |
| `http-proxy` | чейнинг через прокси: шлёт CONNECT на фиксированный `addr` сквозь предыдущий стрим | принимает HTTP CONNECT от браузера и достаёт адрес назначения |
| `tls` | outbound-рукопожатие: `sni` и настраиваемый отпечаток | терминирует TLS: выбирает сертификат по SNI (`certs`/`default`) и выполняет рукопожатие |
| `http2` | открывает POST/PUT-запрос и отдаёт наружу **виртуальный стрим** | принимает HTTP/2-запросы и отдаёт каждый дальше как отдельный виртуальный поток |
| `jitter` | добавляет случайную задержку перед каждой записью; см. [docs/ru/shaping.md](docs/ru/shaping.md) | то же, для записей своей стороны |
| `fragment` | режет каждую запись на более мелкие части; см. [docs/ru/shaping.md](docs/ru/shaping.md) | то же, для записей своей стороны |
| `vless` | протокол: заворачивает стрим во фрейминг VLESS — заголовок с аутентификацией по UUID (команда TCP), адрес цели, затем полезная нагрузка | протокол: распаковывает фрейминг VLESS, проверяет UUID, коннектится к цели и соединяет оба конца |
| `pad` | выравнивание размеров, чистый шейпер (`stages`, без ключей; см. [docs/ru/shaping.md](docs/ru/shaping.md)) | то же |
| `auth` | аутентификация кадров: HMAC-тэг на каждую запись, один общий ключ, без хендшейка; см. [docs/ru/auth.md](docs/ru/auth.md) | то же (ключ идентичен на обеих концах) |
| `xhttp2` | Разделяет туннель на upload (`POST`/`PUT`) и download (`GET`), отдавая наружу один **виртуальный стрим**. | Связывает upload- и download-запросы по настроенному заголовку Session ID независимо от порядка их прихода. |


Порядок важен для `pad`: `tcp → tls → pad` прячет паддинг внутри шифрования (рекомендуется). `tcp → pad → tls` тоже работает, но светит формат кадров DPI. `pad` не аутентифицирует; ставь под ним слой `auth` (`tcp → tls → auth → pad → протокол`; см. [docs/ru/auth.md](docs/ru/auth.md)).

Слой `http2` или любой мультиплексирующий транспорт забирает сокет, а наружу отдаёт виртуальный стрим. Поэтому протоколу всё равно, что под ним: голый TCP, TLS или HTTP/2. Он просто читает и пишет поток.

### Пример: клиент

```toml
# 1. вход: слушаем локальный порт и разбираем HTTP CONNECT
[[inbound.layers]]
type = "tcp"
addr = "127.0.0.1:10810"

[[inbound.layers]]
type = "http-proxy"

# 2. выход: туннель до сервера
[[outbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[outbound.layers]]
type = "tls"
sni = "domain.com"
tls_path = "./tls.toml"
http2_path = "./http2.toml"   # читается только при alps = true

[[outbound.layers]]
type = "http2"
path = "/tun"
host = "idk.com"
method = "POST"
config = "./http2.toml"

[[outbound.layers]]
type = "vless"     # протокол всегда последний
uuid = "11111111-1111-4111-8111-111111111111"   # заглушка, сгенерируйте свой
```

Что происходит:

1. `tcp` в inbound слушает адрес (это делает любой входной источник).
2. `http-proxy` достаёт из запроса адрес назначения и передаёт его протоколу, чтобы тот пометил пакеты. На этом inbound закончен. Вместо HTTP CONNECT можно написать свой входной слой, например SOCKS5: его задача только достать адрес назначения.
3. В outbound `tcp` создаёт сокет и подключает его к серверу, `tls` шифрует его, `http2` оборачивает в виртуальный стрим, а протокол работает уже с ним.

### Пример: сервер

```toml
[[inbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[inbound.layers]]
type = "tls"
certs = [
    { sni = "domain.com", cert = "/path/to/fullchain.pem", key = "/path/to/privkey.pem" },
]
default = "domain.com"
alpn = ["h2"]

[[inbound.layers]]
type = "http2"
path = "/tun"
host = "idk.com"
method = "POST"

[[inbound.layers]]
type = "vless"
uuid = "11111111-1111-4111-8111-111111111111"   # тот же UUID, что и в outbound-конфиге

[[outbound.layers]]
type = "tcp"        # без адреса: подключаемся туда, куда попросил протокол
```

Здесь те же слои, но работают они как акцепторы:

- `tls` принимает сокет, выбирает сертификат по SNI из ClientHello (`certs`/`default`), делает рукопожатие и отдаёт его дальше;
- `http2` это HTTP/2-сервер: принимает только запросы с совпадающими `method`, `path` и `host`, остальным отвечает 404;
- затем вызывается **функция протокола на inbound**, которой передаётся стрим;
- `tcp` в outbound без адреса подключается к цели, которую назвал протокол.

## Настройка отпечатков

И TLS, и HTTP/2 настраиваются целиком. Cray умеет задавать значения вручную, профилей пока что нету.

```toml
# tls.toml
cipher_suites = [
    "TLS_AES_128_GCM_SHA256",
    "TLS_AES_256_GCM_SHA384",
    "TLS_CHACHA20_POLY1305_SHA256",
    "ECDHE-ECDSA-AES128-GCM-SHA256",
    "ECDHE-RSA-AES128-GCM-SHA256",
]
alpn = ["h2"]
curves = ["X25519", "P-256", "P-384"]
signature_algorithms = [
    "rsa_pkcs1_sha256",
    "rsa_pkcs1_sha384",
    "ecdsa_secp256r1_sha256",
]
permute_extensions = true
```

Отпечатки лежат в отдельных файлах профилей, на которые указывают слои: `tls_path` (TLS) и `config` (HTTP/2). HTTP/2-профиль `http2.toml` описывает SETTINGS, порядок псевдозаголовков и заголовков, приоритеты.

Подробное описание всех полей: [docs/ru/tls.md](docs/ru/tls.md) и [docs/ru/http2.md](docs/ru/http2.md).

На сервере слой `tls` берёт `alpn` напрямую; `tls_path` в inbound игнорируется (пишется warning).

## Модули

| Модуль | Роль |
|---|---|
| `core/` | Движок: контракт слоёв (`Layer`), `Registry`, сборка и проверка цепочек, прогон `drive`. Имён слоёв не знает. |
| `layers/` | Все слои по видам: `transport/` (`tls`, `http2`), `proxy/` (`http-proxy`), `protocol/` (`vless`), `wrapers/` (`jitter`, `fragment`), плюс `tcp`, `unix`, билдеры `fingerprint/` и загрузка `profiles/`. Новый слой — один файл + одна строка `register`. |
| `cray/` | Бинарь: разбор аргументов, регистрация слоёв, сборка движка, запуск. |

## Запуск

Для сборки нужны Rust, `cmake` и C/C++-компилятор (TLS построен на BoringSSL через `btls`).

```bash
cargo build --release
cd conf          # пути к профилям вроде ./tls.toml отсчитываются от рабочей директории
../target/release/cray --config client.toml
../target/release/cray --config server.toml
```

Примеры конфигов и профилей лежат в [`conf/`](conf/).

Свой UUID сгенерируйте командой `cargo run -p cray --bin gen_uuid` и укажите его в поле `uuid` слоя `vless` на обеих сторонах. UUID в примерах это заглушки, не используйте их.

### Логирование

Уровень по умолчанию `info`. Чтобы изменить его, задайте `RUST_LOG`, глобально или для отдельных тегов:

```bash
RUST_LOG=info ./cray --config server.toml
RUST_LOG=info,TLS=debug,FRAG=trace ./cray --config client.toml
```

Теги: `CHAIN`, `INB`, `HTTP`, `TLS`, `VLESS`, `JITTER`, `FRAG`. Подробности по каждому соединению пишутся на уровнях `debug` и `trace`, поэтому `info` остаётся тихим.

## Статус

- слои `tcp`, `unix`, `tls`, `http2`, `xhttp2`, `http-proxy` и обёртки `jitter`, `fragment`, `pad`;
- Слой `xhttp2`: разделяет туннель на два HTTP/2-потока и связывает upload (`POST`/`PUT`) с download (`GET`) по настраиваемому заголовку Session ID независимо от порядка прихода запросов. Данные передаются потоком без буферизации всего сообщения; см. [docs/ru/xhttp2.md](docs/ru/xhttp2.md).

- слой `auth`: аутентификация каждого кадра HMAC (v1 — только тэг, защиты от
  повторов пока нет); см. [docs/ru/auth.md](docs/ru/auth.md).
- сборка inbound- и outbound-цепочек из конфига, проверка порядка слоёв;
- протокол `vless` (команда TCP, аутентификация по UUID).

> ⚠️ `vless` пока лишь частично следует формату заголовка VLESS и **не совместим** с Xray, sing-box и другими VLESS-клиентами. Отличия: для доменов и IPv6 используются коды адресов 3 и 4 как в SOCKS5 (в VLESS это 2 и 3), сервер не отправляет заголовок ответа, дополнения запроса считаются пустыми, поддерживается только команда TCP. Клиент Cray работает с сервером Cray. UUID это единственный секрет, защиты от повторов пока нет.

**Планы:**
1. Полная совместимость с VLESS (см. предупреждение выше), команды UDP и Mux, защита от повторов (nonce-кэш).
2. `auth`: защита от повторов (кэш nonce и маскированная метка времени, хендшейка
   по-прежнему нет) и AEAD-режим записи (`[nonce:16 | ts':8 | len:2 | AEAD(payload)]`).
3. Двухуровневая проверка: уровень 1 на стороне nginx (HMAC-кука, timestamp, при отсутствии куки честный статик-сайт), уровень 2 в протоколе (при отказе зеркало настоящей страницы ошибки, а не TCP RST).
4. Декларативное описание протокола (DSL) для тех, кто не хочет писать Rust-код. Rust-авторы остаются со свободными руками, DSL ограничен закрытым набором верификаторов.
5. Свои транспорты и протоколы как расширения, HTTP/1.1 и WebSocket поверх, UDP.
6. Мультиплексирование соединений (в последнюю очередь).
7. `xhttp`: развал аплинка и даунлинка на две ноги с независимыми стеками.
   Каждая нога (`up`/`down`) — полноценная подцепочка со своими транспортами
   и шейпингом, так что направления выглядят на проводе по-разному:

```toml
[[outbound.layers]]
type = "xhttp-h2"
host = "idk.com"
path = "/tun"
method = "POST"
config = "conf/http2.toml"
# Каждая нога — полноценная подцепочка: внутрь можно любые слои, кроме лишних
# транспортов (h2/ws — tcp/tls не в счёт) и протоколов. Шейпинг (jitter,
# fragment, pad), другое шифрование вместо/внутри tls, ноги через разные
# прокси через http-proxy:
up = [
  { type = "tcp", addr = "up.example.com:443" },
  { type = "http-proxy", addr = "xhttp.server.com:443" },
  { type = "tls", sni = "xhttp.server.com", tls_path = "./tls.toml" },
]
down = [
  { type = "tcp", addr = "down.example.com:443" },
  { type = "tls", sni = "down.example.com", tls_path = "./tls.toml" },
]
```
