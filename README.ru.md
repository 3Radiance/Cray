# Cray

[English](README.md) | Русский

[![CI](https://github.com/3Radiance/Cray/actions/workflows/ci.yml/badge.svg)](https://github.com/3Radiance/Cray/actions/workflows/ci.yml)

**Компонуемый прокси-движок на Rust.**

Cray собирает соединение из независимых слоёв, которые описываются в TOML-файле: источник соединений, любое число транспортов и протокол в конце. Транспорт и протокол ничего не знают друг о друге, поэтому новый протокол работает поверх любого транспорта, а новый транспорт несёт любой протокол.

```text
tcp → протокол
tcp → tls → протокол
tcp → tls → http2 → протокол
tcp → tls → xhttp2 → auth → протокол
```

> 🚧 Проект в активной разработке. Слоёвое ядро работает; чего пока не хватает, см. [Статус](#статус).

---

## Обзор

### Что это

Прокси-движок, а не готовый VPN: небольшое ядро, которое исполняет цепочку слоёв, и набор слоёв поверх него. Один и тот же бинарник работает клиентом или сервером в зависимости только от конфига.

### Зачем

В большинстве прокси-ядер протокол привязан к транспорту: новый транспорт означает переписывание протокола, а то, как трафик выглядит в сети, решает автор. Cray разделяет эти две вещи и переносит в конфигурацию все решения, которые формируют трафик.

### Принципы

- **Компонуемость.** Слои комбинируются свободно. Протокол читает и пишет поток, и ему всё равно, что под ним: голый TCP, TLS или HTTP/2.
- **Явность.** Имена заголовков, отпечатки, страницы ответов и отказов это значения в конфиге и профилях, а не константы в коде.
- **Контроль.** Cray даёт механизмы, а не политики: какие слои соединять, как формировать трафик и как он выглядит в сети, решаете вы в конфиге.

## Концепции

### Цепочки и роли

Конфигурация это TOML-файл с двумя цепочками слоёв:

- **`inbound.layers`**: как принять соединение;
- **`outbound.layers`**: как выйти дальше.

Роль определяется позицией, переключателя client/server нет. Inbound-слои слушают и принимают, outbound-слои звонят. Протокол в конце `outbound.layers` означает, что эта сторона инициирует; в конце `inbound.layers` означает, что принимает.

**Правила цепочки:**
- первый слой это источник соединений (`tcp` или `unix`);
- остальные слои это транспорты, каждый превращает поток в поток;
- **протокол всегда последний** и завершает соединение.

### Слои

| Слой | outbound | inbound |
|---|---|---|
| `tcp` | подключается к `addr`; без `addr` — прямое соединение к цели (как «freedom/direct») | слушает `addr` |
| `unix` | подключается к `addr` | слушает `addr` |
| `http-proxy` | чейнинг через прокси: шлёт CONNECT на фиксированный `addr` сквозь предыдущий стрим | принимает HTTP CONNECT от браузера и достаёт адрес назначения |
| `tls` | outbound-рукопожатие: `sni` и настраиваемый отпечаток | терминирует TLS: выбирает сертификат по SNI (`certs`/`default`) и выполняет рукопожатие |
| `http2` | открывает один POST/PUT-запрос и отдаёт наружу **виртуальный стрим** | принимает HTTP/2-запросы и отдаёт каждый подходящий дальше как отдельный виртуальный поток; всё остальное получает настраиваемый отказ (статус, заголовки, HTML-страница) |
| `xhttp2` | разделяет туннель на upload (`POST`/`PUT`) и download (`GET`) и отдаёт наружу один **виртуальный стрим**. `mode`: `StreamUp` (один стримящийся `POST`) или `PacketUp` (по `POST` на кусок, порядок задаёт номер) | связывает запросы одной сессии по настроенному заголовку Session ID независимо от порядка прихода; в `PacketUp` ещё и восстанавливает порядок пакетов |
| `jitter` | добавляет случайную задержку перед каждой записью; см. [docs/ru/shaping.md](docs/ru/shaping.md) | то же, для записей своей стороны |
| `fragment` | режет каждую запись на более мелкие части; см. [docs/ru/shaping.md](docs/ru/shaping.md) | то же, для записей своей стороны |
| `pad` | выравнивание размеров, чистый шейпер (`stages`, без ключей; см. [docs/ru/shaping.md](docs/ru/shaping.md)) | то же |
| `auth` | аутентификация кадров: HMAC-тэг на каждую запись, один общий ключ, без хендшейка; см. [docs/ru/auth.md](docs/ru/auth.md) | то же (ключ идентичен на обоих концах) |
| `vless` | протокол: заворачивает стрим во фрейминг VLESS — заголовок с аутентификацией по UUID (команда TCP), адрес цели, затем полезная нагрузка | протокол: распаковывает фрейминг VLESS, проверяет UUID, коннектится к цели и соединяет оба конца |
| `pipe` | — | локальный протокол для тестирования и локального прозрачного прокси без сервера: конфига нет; берёт адрес цели из контекста (`ConnectRequest`, его поставляет, например, `http-proxy`), дозванивается до неё через outbound-цепочку (`Dialer`) и сшивает оба конца соединения, пока не упрётся в EOF. Из `Cx` требует только эти два ключа. |

Порядок важен для `pad`: `tcp → tls → pad` прячет паддинг внутри шифрования (рекомендуется). `tcp → pad → tls` тоже работает, но светит формат кадров DPI. `pad` не аутентифицирует; ставь под ним слой `auth` (`tcp → tls → auth → pad → протокол`; см. [docs/ru/auth.md](docs/ru/auth.md)).

`http2`, `xhttp2` и любой другой мультиплексирующий транспорт забирают сокет и отдают наружу виртуальный стрим, поэтому протокол сверху читает и пишет обычный поток байтов.

## Примеры

### Клиент

```toml
# 1. Inbound: слушаем локальный порт и разбираем HTTP CONNECT
[[inbound.layers]]
type = "tcp"
addr = "127.0.0.1:10810"

[[inbound.layers]]
type = "http-proxy"

# 2. Outbound: туннель до сервера
[[outbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[outbound.layers]]
type = "tls"
sni = "domain.com"
tls_path = "./tls.toml"
http2_path = "./http2.toml"   # читается только при alps = true

[[outbound.layers]]
type = "http2"
path = "/tun"
host = "idk.com"
method = "POST"
config = "./http2.toml"

[[outbound.layers]]
type = "vless"     # протокол всегда последний
uuid = "11111111-1111-4111-8111-111111111111"   # заглушка, сгенерируйте свой
```

Что происходит:

1. `tcp` в inbound слушает указанный адрес (так делает любой inbound-источник).
2. `http-proxy` достаёт адрес назначения из запроса и передаёт его протоколу, чтобы тот пометил пакеты. На этом inbound-цепочка заканчивается. Вместо HTTP CONNECT можно написать собственный входной слой, например SOCKS5; его единственная задача — извлечь адрес назначения.
3. В outbound `tcp` создаёт сокет и подключает его к серверу, `tls` шифрует, `http2` заворачивает в виртуальный стрим, а протокол работает с этим стримом.

### Сервер

```toml
[[inbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[inbound.layers]]
type = "tls"
certs = [
    { sni = "domain.com", cert = "/path/to/fullchain.pem", key = "/path/to/privkey.pem" },
]
default = "domain.com"
alpn = ["h2"]

[[inbound.layers]]
type = "http2"
path = "/tun"
host = "idk.com"
method = "POST"

[[inbound.layers]]
type = "vless"
uuid = "11111111-1111-4111-8111-111111111111"   # тот же UUID, что в outbound-конфиге

[[outbound.layers]]
type = "tcp"        # без адреса: подключаемся к цели, которую запросил протокол
```

Те же слои здесь работают как принимающие:

- `tls` принимает сокет, выбирает сертификат по SNI из ClientHello (`certs`/`default`), делает рукопожатие и передаёт дальше. `alpn` задаётся прямо на слое;
- `http2` это HTTP/2-сервер: он принимает только запросы с подходящими `method`, `path` и `host`, остальные отклоняет (по умолчанию 404, настраивается в профиле);
- затем **inbound-протоколу** отдаётся стрим;
- `tcp` в outbound без адреса подключается к цели, которую передал протокол.

### Разделение туннеля через `xhttp2`

`xhttp2` заменяет `http2`, когда один стримящийся запрос создаёт проблему, например за CDN, который буферизует тела запросов. Клиент ниже отправляет download одним длинным `GET`, а upload много короткими `POST`; сервер стоит за reverse proxy, который терминирует TLS.

```toml
# клиент
[[outbound.layers]]
type = "tcp"
addr = "cdn.example.com:443"

[[outbound.layers]]
type = "tls"
sni = "cdn.example.com"
tls_path = "./tls.toml"

[[outbound.layers]]
type = "xhttp2"
host = "cdn.example.com"
path = "/api/sync"
method = "POST"
config = "./xhttp2.toml"   # задаёт заголовки Session ID и порядкового номера
mode = "PacketUp"          # или "StreamUp"

[[outbound.layers]]
type = "vless"
uuid = "11111111-1111-4111-8111-111111111111"
```

```toml
# сервер (за reverse proxy)
[[inbound.layers]]
type = "tcp"
addr = "127.0.0.1:10811"

[[inbound.layers]]
type = "xhttp2"
host = "cdn.example.com"
path = "/api/sync"
method = "POST"
config = "./xhttp2.toml"
mode = "PacketUp"          # должен совпадать с клиентом

[[inbound.layers]]
type = "vless"
uuid = "11111111-1111-4111-8111-111111111111"

[[outbound.layers]]
type = "tcp"
```

Режимы, маркеры заголовков `id` и `seq` и заметки о работе за CDN описаны в [docs/ru/xhttp2.md](docs/ru/xhttp2.md). Пример профиля лежит в [`conf/xhttp2.toml`](conf/xhttp2.toml).

## Профили

TLS и HTTP/2 настраиваются полностью. Cray позволяет задавать значения вручную, а готовые пресеты лежат в [`conf/fingerprint/`](conf/fingerprint/README.ru.md): браузерные профили, перенесённые из wreq-util скриптом, поэтому в них могут быть неточности.

```toml
# tls.toml
cipher_suites = [
    "TLS_AES_128_GCM_SHA256",
    "TLS_AES_256_GCM_SHA384",
    "TLS_CHACHA20_POLY1305_SHA256",
    "ECDHE-ECDSA-AES128-GCM-SHA256",
    "ECDHE-RSA-AES128-GCM-SHA256",
]
alpn = ["h2"]
curves = ["X25519", "P-256", "P-384"]
signature_algorithms = [
    "rsa_pkcs1_sha256",
    "rsa_pkcs1_sha384",
    "ecdsa_secp256r1_sha256",
]
permute_extensions = true
```

Отпечатки лежат в отдельных файлах профилей, на которые указывают слои: `tls_path` (TLS) и `config` (HTTP/2 и `xhttp2`). Профиль HTTP/2 описывает SETTINGS, порядок псевдозаголовков и заголовков, приоритеты, а на сервере ещё и ответы и страницы отказов. Outbound-слои загружают и проверяют профили при сборке цепочки, поэтому сломанный профиль останавливает программу на старте.

Подробные справочники по полям: [docs/ru/tls.md](docs/ru/tls.md), [docs/ru/http2.md](docs/ru/http2.md) и [docs/ru/xhttp2.md](docs/ru/xhttp2.md).

На сервере слой `tls` принимает `alpn` напрямую; `tls_path` в inbound игнорируется (в лог пишется предупреждение).

## Структура проекта

| Путь | Назначение |
|---|---|
| `core/` | Движок: контракт слоя (`Layer`), `Registry`, сборка и проверка цепочек, исполнитель `drive`. Не знает имён слоёв. |
| `layers/` | Все слои по видам: `transport/` (`tls`, `http2`, `xhttp2`), `proxy/` (`http-proxy`), `protocol/` (`vless`, `pipe`), `wrappers/` (`jitter`, `fragment`, `pad`, `auth`), а также `tcp`, `unix`, билдеры `fingerprint/` и загрузка `profiles/`. Новый слой это один файл плюс одна строка `register`. |
| `cray/` | Бинарник: разбирает аргументы, регистрирует слои, собирает движок, запускает. |
| `conf/` | Примеры конфигов и профилей; в `conf/fingerprint/` лежат браузерные пресеты, сгенерированные из wreq-util. |
| `tools/` | `fetch_wreq_profiles.sh` скачивает исходники wreq-util, `gen.py` превращает их в `conf/fingerprint/`. |
| `docs/` | Справочники по слоям и профилям на английском (`eng/`) и русском (`ru/`). |

## Сборка и запуск

Для сборки нужны Rust, `cmake` и компилятор C/C++ (TLS построен на BoringSSL через `btls`).

```bash
cargo build --release
cd conf          # пути профилей вроде ./tls.toml считаются от рабочей директории
../target/release/cray --config client.toml
../target/release/cray --config server.toml
```

Примеры конфигов и профилей лежат в [`conf/`](conf/).

Сгенерируйте свой UUID командой `cargo run -p cray --bin gen_uuid` и впишите его в поле `uuid` слоя `vless` на обеих сторонах. UUID в примерах это заглушки, не используйте их.

### Логирование

Уровень по умолчанию `info`. Меняется через `RUST_LOG`, глобально или по тегу:

```bash
RUST_LOG=info ./cray --config server.toml
RUST_LOG=info,TLS=debug,FRAG=trace ./cray --config client.toml
```

Теги: `CHAIN`, `INB`, `HTTP`, `TLS`, `CERT`, `H2`, `XH2`, `VLESS`, `JITTER`, `FRAG`, `PAD`. Подробности по каждому соединению пишутся на уровнях `debug` и `trace`, поэтому `info` остаётся тихим.

## Статус

### Работает

- Слои `tcp`, `unix`, `http-proxy`, `tls`, `http2`, `xhttp2`, `pipe` и `vless`, а также обёртки `jitter`, `fragment`, `pad` и `auth`.
- Сборка inbound- и outbound-цепочек из конфига и проверка порядка слоёв.
- `http2`: HTTP/2-клиент с профилем и сервер с настраиваемыми ответами и отказами; см. [docs/ru/http2.md](docs/ru/http2.md).
- `xhttp2`: upload и download разнесены по отдельным HTTP/2-запросам и связываются по заголовку Session ID на ваш выбор. `StreamUp` стримит upload одним `POST`; `PacketUp` отправляет его упорядоченными `POST`-пакетами с восстановлением порядка через персональный буфер реордера сессии и прогнан через Cloudflare и nginx. Простаивающие и несопоставленные сессии удаляет фоновый GC. См. [docs/ru/xhttp2.md](docs/ru/xhttp2.md).
- `auth`: покадровая HMAC-SHA256-аутентификация; см. [docs/ru/auth.md](docs/ru/auth.md).
- `vless`: команда TCP с аутентификацией по UUID.

### Известные ограничения

> ⚠️ `vless` лишь частично следует раскладке заголовка VLESS и пока **не совместим** с Xray, sing-box и другими VLESS-клиентами. Отличия: типы адресов домена и IPv6 используют коды в стиле SOCKS5 — 3 и 4 (в VLESS это 2 и 3), сервер не шлёт заголовок ответа, request addons считаются пустыми, поддерживается только команда TCP. Клиент Cray работает с сервером Cray. UUID это единственный секрет, защиты от повторного воспроизведения пока нет.

- `auth` v1 несёт только тэг: защиты от повторного воспроизведения пока нет.
- `xhttp2` `PacketUp`: сервер пока не ограничивает буфер реордера и число сессий. Простаивающие и несопоставленные сессии удаляет встроенный GC. Каждая запись уходит сразу отдельным запросом — write-through по дизайну, без буферизации записей.
- Пресеты TLS и HTTP/2 в `conf/fingerprint/` сгенерированы скриптом и могут содержать ошибки. Поля, которые stock btls выразить не может (подписи ML-DSA, `grease_sigalgs_enabled`, `random_aes_hw_override`, PSK), пропущены; см. [conf/fingerprint/README.ru.md](conf/fingerprint/README.ru.md).

### Планы

1. Укрепление `xhttp2`: лимиты на буфер реордера и таблицу сессий.
2. Полная совместимость VLESS на уровне формата (см. предупреждение выше), команды UDP и Mux, защита от повторного воспроизведения (кэш nonce).
3. `auth`: защита от повторного воспроизведения (кэш nonce и маскированный timestamp, всё ещё без хендшейка) и AEAD-режим записей (`[nonce:16 | ts':8 | len:2 | AEAD(payload)]`).
4. Двухуровневая проверка: уровень 1 на стороне nginx (HMAC-cookie, timestamp; если cookie нет, отдаётся настоящий статический сайт), уровень 2 в протоколе (при отказе показывать зеркало настоящей страницы ошибки, а не TCP RST).
5. Декларативный язык описания протоколов (DSL) для тех, кто не хочет писать Rust. У авторов на Rust остаётся полная свобода; DSL ограничен закрытым набором верификаторов.
6. Кастомные транспорты и протоколы как расширения, поддержка HTTP/1.1 и WebSocket, UDP.
7. Мультиплексирование соединений (низший приоритет).
8. Независимые стеки для каждой ноги разделённого транспорта. Каждая нога (`up`/`down`) станет полноценной подцепочкой со своими транспортами и шейпингом, так что два направления смогут выглядеть в сети по-разному:

```toml
[[outbound.layers]]
type = "xhttp-h2"
host = "idk.com"
path = "/tun"
method = "POST"
config = "conf/http2.toml"
# Каждая нога — полноценная подцепочка: внутрь можно любые слои, кроме лишних
# транспортов (h2/ws — tcp/tls не в счёт) и протоколов. Шейпинг (jitter,
# fragment, pad), другое шифрование вместо/внутри tls, ноги через разные
# прокси через http-proxy:
up = [
  { type = "tcp", addr = "up.example.com:443" },
  { type = "http-proxy", addr = "xhttp.server.com:443" },
  { type = "tls", sni = "xhttp.server.com", tls_path = "./tls.toml" },
]
down = [
  { type = "tcp", addr = "down.example.com:443" },
  { type = "tls", sni = "down.example.com", tls_path = "./tls.toml" },
]
```
